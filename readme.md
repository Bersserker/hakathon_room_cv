# Проект классификации типов помещений

Проект решает задачу классификации фотографий помещений из объявлений недвижимости. Модель получает одно изображение и возвращает номер класса, название помещения, вероятность ответа и несколько наиболее вероятных вариантов.

В репозитории есть всё, что нужно для повторного запуска: подготовка данных, обучение, оценка качества, получение предсказаний, проверка итогового CSV, демо-приложение и запуск через Docker.

## Описание проекта

### Зачем это нужно

В объявлениях недвижимости тип помещения часто проверяют вручную. Это занимает время, а ошибки в разметке портят фильтры, поиск, рекомендации и аналитику.

Задача усложняется тем, что фотографии бывают разного качества и сняты с разных ракурсов. Некоторые классы похожи друг на друга: например, спальня, гостиная и универсальная комната. Есть и редкие классы, по которым модели обычно ошибаются чаще.

Модель можно использовать как подсказку для модератора. Для уверенных ответов её можно позже подключить к частичной автоматизации.

### Что делает модель

Тип задачи: классификация изображений на 20 классов.

- Вход: фотография помещения или объекта из объявления.
- Выход: класс от `0` до `19`.
- Главная метрика: Macro F1. Она важна, потому что обычная точность может скрывать плохое качество на редких классах.
- Дополнительные проверки: F1 по каждому классу, матрица ошибок, предсказания на отложенных частях разбиения и отдельной проверочной выборке.
- Итоговый файл для отправки: CSV с колонками `image_id_ext,Predicted`.

Схема классов хранится в конфигурационном файле `configs/data/class_mapping.yaml`:

| ID | Класс |
|---:|---|
| 0 | кухня / столовая |
| 1 | кухня-гостиная |
| 2 | универсальная комната |
| 3 | гостиная |
| 4 | спальня |
| 5 | кабинет |
| 6 | детская |
| 7 | ванная комната |
| 8 | туалет |
| 9 | совмещенный санузел |
| 10 | коридор / прихожая |
| 11 | гардеробная / кладовая / постирочная |
| 12 | балкон / лоджия |
| 13 | вид из окна / с балкона |
| 14 | дом снаружи / двор |
| 15 | подъезд / лестничная площадка |
| 16 | другое |
| 17 | предметы интерьера / быт.техника |
| 18 | не могу дать ответ / не ясно |
| 19 | комната без мебели |

### Как работает решение

Общий путь данных:

```text
фото объявления
  -> подготовка изображения
  -> модель классификации
  -> вероятности по классам
  -> несколько самых вероятных классов
  -> модерация, поиск, демо-приложение или серверный интерфейс
```

Пример ответа модели. Имена `class_id`, `class_name`, `probability` и `top_k` оставлены как поля JSON, потому что такие названия использует код:

```json
{
  "class_id": 3,
  "class_name": "гостиная",
  "probability": 0.87,
  "top_k": [
    {"class_id": 3, "class_name": "гостиная", "probability": 0.87},
    {"class_id": 1, "class_name": "кухня-гостиная", "probability": 0.08},
    {"class_id": 2, "class_name": "универсальная комната", "probability": 0.03}
  ]
}
```

### Как устроен процесс

Проект построен как цепочка шагов, которые можно повторить на другом компьютере:

```text
исходные CSV и изображения
  -> проверка файлов и таблица с путями
  -> разбиение без утечки данных
  -> обучение моделей
  -> оценка качества
  -> отчёты и журнал опытов
  -> конфигурационный файл итоговой версии
  -> получение предсказаний
  -> проверенный файл отправки
```

Основные шаги:

1. Проверка данных: наличие изображений, открываемость файлов, расчёт `content_hash`, отчёты по качеству.
2. Разбиение данных: 5 частей для обучения и отдельная проверочная выборка. Проверяем, чтобы одинаковые объекты и одинаковые изображения не попадали одновременно в обучение и проверку.
3. Обучение: модели PyTorch и timm, преобразования изображений, функция потерь, выбор примеров для пакетов данных, сохранение весов.
4. Журнал опытов: MLflow сохраняет параметры, метрики, метки и файлы результата.
5. Оценка качества: предсказания на отложенных частях, отдельная проверочная выборка, F1 по классам и матрица ошибок.
6. Итоговая версия: файл весов, конфигурационный файл итоговой версии, команда получения предсказаний, проверка итогового CSV, демо-приложение и серверный интерфейс.

Подробное описание лежит в файле документации `docs/ARCHITECTURE.md`.

### Модели, опыты и результат

В проекте проверялись разные основы моделей и способы работы с дисбалансом классов: ConvNeXt, EfficientNet, ResNet, ViT/CLIP, взвешенная функция потерь, Focal Loss, сбалансированный выбор примеров и поправки к вероятностям классов.

По материалам финальной защиты основной исследовательский кандидат был таким:

- основа модели: `convnext_xlarge.fb_in22k_ft_in1k_384`;
- размер входного изображения: `512x512`;
- функция потерь: Focal Loss;
- выбор примеров: сбалансированный;
- обучение: ранняя остановка, смешанная точность `AMP`, экономия памяти при расчёте градиентов;
- итог на презентации: `final_oof_macro_f1 ≈ 0.7934`.

В репозитории также зафиксирован воспроизводимый вариант для текущей итоговой версии:

- конфигурационный файл итоговой версии: `configs/release/rc1.yaml`;
- кандидат итоговой версии: `release_cv03_balanced_sampler_trainval_90_10`;
- основа модели: `convnext_tiny.in12k_ft_in1k`;
- файл весов модели: `artifacts/checkpoints/release_cv03_balanced_sampler_trainval_90_10.ckpt`.

### Журнал опытов и воспроизводимость

Все серьёзные запуски записываются в MLflow. По умолчанию используется локальная база SQLite:

```yaml
mlflow:
  tracking_uri: sqlite:///artifacts/logs/mlflow.db
  experiment_name: room_type_image_baseline
  artifact_root: artifacts/logs/mlruns
```

Для кандидата итоговой версии сохраняются файл весов, итоговый конфигурационный файл, предсказания на проверочных выборках, команда запуска, отчёт по классам и номер запуска в MLflow. Метрики без номера запуска не используются для выбора модели.

Подробнее об этом написано в файлах документации `docs/ML_FLOW.md` и `docs/project-rules.md`.

### Правила работы над проектом

Основные правила описаны в файле документации `docs/project-rules.md`:

- в `main` напрямую никто не отправляет изменения;
- запрос на слияние должен быть связан с задачей и содержать описание изменений, способ запуска, номер запуска в MLflow или ссылку на файл результата;
- изменения в обучении и получении предсказаний должны проходить быструю проверку;
- результат только в ноутбуке не считается завершённой задачей, если нет отдельного скрипта или конфигурационного файла;
- изменения в разбиении данных, обучении модели, итоговой версии, Docker и серверном интерфейсе требуют профильной проверки другим участником.

## Быстрый запуск проекта

Положите данные в `data/raw/`:

```text
data/raw/
├── train_df.csv
├── val_df.csv
├── test_df.csv
├── train_images/train_images/*.jpg
├── val_images/val_images/*.jpg
└── test_images/test_images/*.jpg
```

Локальный запуск:

```bash
uv sync
make full-pipeline
```

Команда создаёт `data/preprocess/`, проверяет утечку данных, обучает 5 частей разбиения, получает предсказания и пишет файл `releases/full_pipeline/submission.csv`.

Запуск Docker на процессоре:

```bash
docker compose build
docker compose run --rm notebook make full-pipeline
```

Запуск Docker с видеокартой NVIDIA:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml build
docker compose -f docker-compose.yml -f docker-compose.gpu.yml run --rm notebook make full-pipeline
```

Только Jupyter:

```bash
docker compose up
# http://localhost:8888/tree?token=room-cv
```

## Схема классов, предсказания и файл отправки

В данных используется 20 классов: `0..19`. Это подтверждено файлами `train_df.csv` и `room_type_sample_submission.csv`.

Важно:

- класс `18` — `не могу дать ответ / не ясно`;
- класс `19` — `комната без мебели`.

Итоговый CSV должен иметь ровно две колонки:

```csv
image_id_ext,Predicted
```

Текущий конфигурационный файл итоговой версии `configs/release/rc1.yaml` использует файл весов модели `artifacts/checkpoints/release_cv03_balanced_sampler_trainval_90_10.ckpt`.

Файлы схемы и аудита:

- конфигурационный файл схемы классов: `configs/data/class_mapping.yaml`
- отчёт аудита схемы: `reports/class_schema_audit.md`

Создать файл отправки:

```bash
uv run python -m src.inference.predict --config configs/release/rc1.yaml
```

Проверить файл отправки:

```bash
uv run python -m src.inference.validate_submission \
  --submission releases/rc1/submission.csv \
  --test-csv data/raw/test_df.csv \
  --class-mapping configs/data/class_mapping.yaml
```

Запустить демо-приложение с конфигурационным файлом итоговой версии `configs/release/rc1.yaml`:

```bash
uv run python demo/app.py --config configs/release/rc1.yaml
```

Подробнее про MLflow: `docs/ML_FLOW.md`.

## Docker

Docker-сценарий в проекте нужен для локальной разработки и запуска Jupyter Notebook в контейнере.

### Установка Docker

1. Установите Docker Desktop для macOS/Windows или Docker Engine с Docker Compose Plugin для Linux.
2. Проверьте, что команды доступны:

```bash
docker --version
docker compose version
```

### Сборка и запуск

Собрать и запустить контейнер:

```bash
docker compose up --build
```

После запуска Jupyter будет доступен по адресу:

```text
http://localhost:8888/tree?token=room-cv
```

Запустить в фоне:

```bash
docker compose up -d --build
```

Остановить проект:

```bash
docker compose down
```

Открыть командную строку внутри контейнера:

```bash
docker compose exec notebook sh
```

Чтобы выйти из командной строки контейнера и вернуться в терминал компьютера:

- введите `exit`;
- или нажмите `Ctrl+D`.

Примечания:

- В контейнер подключается текущая папка проекта, поэтому изменения в ноутбуках и коде сразу видны внутри Docker.
- В `Dockerfile` устанавливаются версии `torch`, `torchvision` и `torchaudio` для процессора, чтобы проект запускался без CUDA.
- Для запуска на видеокарте нужен отдельный набор Docker-файлов и `nvidia-container-toolkit`.

### Docker с видеокартой NVIDIA

Запуск на видеокарте использует файлы `Dockerfile.gpu` и `docker-compose.gpu.yml`.

Требования к компьютеру:

1. Linux с видеокартой NVIDIA, драйвером NVIDIA и NVIDIA Container Toolkit.
2. Или Docker Desktop на Windows с WSL2 и поддержкой видеокарты.
3. Для macOS этот вариант не подходит.

Минимальная подготовка Linux:

```bash
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

Проверить, что Docker видит видеокарту:

```bash
docker run --rm --gpus all nvidia/cuda:12.9.0-base-ubuntu22.04 nvidia-smi
```

Собрать и запустить проект с видеокартой:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build
```

Запустить в фоне:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
```

Проверить CUDA внутри контейнера проекта:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml run --rm notebook \
  uv run python -c "import torch; print(torch.cuda.is_available())"
```

Примечания:

- В образе для видеокарты ставятся зависимости из команды `uv sync --extra cuda`. Они берутся из файла `pyproject.toml`.
- В файле Docker Compose `docker-compose.gpu.yml` доступ к видеокарте описан через поле `devices`.
- Если нужна конкретная видеокарта, вместо `count: all` можно указать `device_ids`.

## Структура проекта

```text
.
├── artifacts/
│   ├── checkpoints/
│   └── logs/
├── configs/
├── data/
│   ├── raw/
│   ├── interim/
│   └── processed/
├── notebooks/
├── reports/
│   └── figures/
├── scripts/
├── src/
│   ├── datasets/
│   ├── models/
│   ├── training/
│   ├── inference/
│   └── utils/
└── tests/
```

Коротко по папкам:

- `src/` — основной код проекта: загрузка данных, модели, обучение, получение предсказаний и вспомогательные функции.
- `src/datasets/` — модули обработки данных: разбиение, аудит и другая логика работы с данными.
- `configs/` — конфигурационные файлы запусков и опытов.
- `data/` — данные на разных стадиях подготовки: исходные, промежуточные и обработанные.
- `notebooks/` — исследовательские ноутбуки Jupyter и быстрые проверки идей.
- `scripts/` — скрипты запуска отдельных частей процесса; внутри тонкие обёртки над кодом из `src/`.
- `artifacts/` — веса моделей, файлы контрольных точек и логи обучения.
- `reports/` — графики, отчёты и итоговые материалы.
- `tests/` — тесты для проверки основной логики проекта.
- `docs/` — документация проекта.
